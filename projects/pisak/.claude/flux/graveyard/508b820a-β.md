## Mission

Implement the NodeLink gateway as specified in `projects/pisak/CONTRACT.md`, as a board plugin at
`board/plugins/pisak/`.

## Approach: the gateway owns the message until it is delivered

Each registered node has a **mailbox** (a bounded FIFO). `/route` puts the envelope in the destination's mailbox and
then:

- `request`: it parks a pending entry keyed by `messageId` and waits for the matching response, up to the timeout.
- `oneway` / `broadcast`: it answers `202` as soon as the message is queued.

A per-node **pump** drains the mailbox by pushing to `deliverUrl`, as the contract says. If push fails, the message
stays queued: a node can then fetch it with an optional `GET /inbox?wait=` long-poll. This is a proposed contract
extension, so pisak must announce it in `#build` before it ships. The pull path makes the gateway survive nodes behind
an unreachable URL, and it lets drop-percentage chaos show up as a measurable redelivery.

### File layout

```
board/plugins/pisak/
├── index.js        # plugin entry, router, JSON body reader with a size cap
├── registry.js     # nodes, tokens, heartbeat state
├── mailbox.js      # bounded queue per node (default 500), overflow → REJECTED reason "queue_full"
├── pump.js         # per-node async drain loop: push with timeout, retry with backoff, breaker gates the pump
├── pending.js      # Map messageId → { resolve, timer } for requests waiting on a response
├── ratelimit.js    # token bucket per source node, checked before enqueue
├── metrics.js      # latency from enqueue to response, queue depth per node, p50/p95, failureDetectionMs
├── events.js       # ring buffer plus SSE
└── admin.js        # kill (drain queues to error), revive, config, reset
```

### Contract mapping

- `heartbeat`: may carry `{ ack: [messageIds] }`, so delivery can be confirmed by heartbeat as well as by push.
- Breaker: when it is open, the pump pauses. Queued requests fail at their own timeout, with `NODE_UNAVAILABLE` and
  `reason: "circuit_open"`.
- `state`: adds `queueDepth` per node. That is a dashboard win: you can *see* back-pressure build up when a node is slow.
- HA (later): mailboxes are plain arrays, so replicating them to instance b is a copy on each enqueue and dequeue.

### Risks you own

- Pump loops must not spin: each pump is a promise chain with `.catch()` that awaits the next item or a 50 ms
  unref'd wait, never `while(true)`.
- Memory: queues and the pending map are bounded, and they are cleared on deregister, kill and reset.
- Extra latency from queueing: measure it against the 5 ms overhead budget.

### Contributing factors

- β's unique value was a pull (long-poll) fallback for nodes behind an unreachable `deliverUrl`, plus heartbeat acks.
  Both became redundant: farzad's nodes live on the same origin (`/t/farzad/n/<id>/deliver`), and farzad agreed in
  `#build` (post 43) that the gateway probes `/t/farzad/n/<id>/heartbeat`.
- The fallback needed a contract extension (`GET /inbox`) that no consumer asked for.
- Queueing adds latency against the 5 ms overhead budget, and it makes `request` semantics harder to keep within
  `ttlMs`.

### Learnings

- "Don't build robustness for a failure mode the peer contract rules out. Check the peers' contracts before forking."
- "`queueDepth` per node is a good dashboard signal. α and γ may expose an in-flight count instead."
